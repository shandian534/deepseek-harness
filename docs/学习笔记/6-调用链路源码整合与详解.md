## 链路一：插件加载与重载循环（Fiber 核心）

### 调用栈回顾

```
apply() → execute() → _execute() → _reload() → _updateState() → _setEpoch() → _refresh() → notify()
```

### 源码整合（按调用顺序）

#### 1. 插件入口：`ctx.plugin()` 注册（`vendor/cordis/src/fiber.ts:265`）

```ts
this.dispose = parent.fiber.effect(() => {
  const remove = runtime.fibers.push(this)         // 把当前 fiber 推入 runtime 的 fiber 列表
  return async () => {
    this.uid = null
    emitPluginDisposed(this.context, this)
    if (this.ctx.registry.has(runtime.callback)) {
      remove()
      if (!runtime.fibers.length) {
        this.ctx.registry.delete(runtime.callback)  // 没有用到这个插件的 fiber 时，从注册表删除
      }
    }
    this._setEpoch(INACTIVE)                         // ← 关键：设置 epoch 为 INACTIVE，触发状态变迁
    // ...
  }
}, 'ctx.plugin()')
```

**难懂点**：
- **`effect()` 是什么**：Cordis 的「注册-拆卸」抽象。传入一个函数 `execute`，立即执行它；如果返回函数/对象，收集成 disposer，在 unload 时自动反向执行
- **`runtime.fibers.push(this)`**：每个插件对应一个 Fiber 实例，`runtime.fibers` 是全局 fiber 列表
- **`_setEpoch(INACTIVE)`**：epoch 是 Fiber 的「代际标记」，变更 epoch 会触发 `_reload`/`_unload`（见下文）

#### 2. Epoch 变更触发重载（`vendor/cordis/src/fiber.ts:625-639`）

```ts
private _setEpoch(epoch: string) {
  const oldEpoch = this._runner.epoch
  if (epoch === oldEpoch) return                  // epoch 没变，什么都不做
  this._runner.epoch = epoch
  if (this.inertia) return                       // inertia 是「正在重载中」的标志，避免递归重载
  this._updateState(() => {                      // ← 关键：状态更新，驱动后续逻辑
    if (epoch !== INACTIVE && oldEpoch === INACTIVE) {
      this.inertia = this._reload()              // 从 INACTIVE → 活跃 epoch：触发重载
      return FiberState.LOADING
    } else {
      this.inertia = this._unload()              // 从活跃 epoch → INACTIVE：触发卸载
      return FiberState.UNLOADING
    }
  })
}
```

**难懂点**：
- **Epoch 是什么**：字符串，格式是 `:::fiber-uid:::fiber-uid:::...`，每个依赖的 fiber uid 拼接。**epoch 变化表示依赖关系变了**，必须重载
- **`inertia` 是什么**：正在重载/卸载中的异步任务指针。设置后，后续 epoch 变化不会触发新的重载（避免递归）
- **为什么先 `inertia = this._reload()` 再返回状态**：`_reload` 是异步的，`inertia` 保存这个 Promise；状态立即返回 LOADING，不会等重载完成

#### 3. 状态更新触发通知（`vendor/cordis/src/fiber.ts:581-595`）

```ts
private _updateState(callback: () => void | FiberState) {
  const oldState = this.state
  this.state = callback() ?? this._getState()
  if (oldState === this.state) return              // 状态没变，什么都不做
  this.context.emit('internal/status', this, oldState)

  // 只在 ACTIVE ↔ NON-ACTIVE 之间切换时通知
  if (oldState !== FiberState.ACTIVE && this.state !== FiberState.ACTIVE) return
  for (const key of Reflect.ownKeys(this.ctx.reflect.store)) {
    const impl = this.ctx.reflect.store[key as symbol]
    if (impl.fiber !== this) continue              // 只通知自己拥有的 impl
    this.ctx.reflect.notify([impl.name])           // ← 调用栈里的 `notify()` 在这里
  }
}
```

**难懂点**：
- **`this.ctx.reflect.store` 是什么**：全局「服务实现注册表」。每个 impl 有一个 fiber 字段，表示「哪个 fiber 拥有这个 impl」
- **为什么只通知 ACTIVE ↔ NON-ACTIVE**：其他状态切换（比如 LOADING → ACTIVE）不需要通知外部；只有「从非活跃变活跃」或「从活跃变非活跃」才需要触发依赖更新
- **`notify()` 的作用**：触发依赖这个 fiber 的其他 fiber 重新执行 `_refresh()`，重新计算 epoch

#### 4. 重新计算依赖 epoch（`vendor/cordis/src/fiber.ts:611-623`）

```ts
_refresh() {
  let epoch: string | boolean = false
  epoch = ''
  for (const name of Object.keys(this.inject)) {    // 遍历所有注入的服务
    const impl = this.store[name]                   // 从 store 取 impl
    if (!impl) {
      epoch = INACTIVE                              // 某个注入的 impl 不可用 → epoch 置为 INACTIVE
      break
    }
    epoch += ':' + impl.fiber.uid                    // 把每个 impl 的 fiber uid 拼进 epoch
  }
  this._setEpoch(epoch)                              // ← 触发下一次 epoch 变更
}
```

**难懂点**：
- **`inject` vs `store`**：`inject` 是「声明要注入的服务名」，`store` 是「实际解析到的 impl」。`_refresh` 检查所有声明是否都有可用 impl
- **Epoch 字符串拼接**：每个 impl 的 fiber uid 用 `:` 拼接。如果任何 impl 不可用（`!impl`），epoch 直接置为 `INACTIVE`
- **循环触发**：`_setEpoch` → `_updateState` → `notify` → 依赖 fiber 的 `_refresh` → `_setEpoch`，形成级联更新

#### 5. 实际重载逻辑（`vendor/cordis/src/fiber.ts:646-673`）

```ts
private async _reload() {
  this.store = { ...this.store }                    // 浅拷贝 store（隔离新旧状态）
  const oldEpoch = this._runner.epoch
  try {
    await Promise.resolve()                          // 确保异步边界
    if (this._runner.epoch === oldEpoch) {           // 确认没有在重载过程中被 invalidate
      this.config = this._resolveConfig(this._config)  // 解析配置（支持 waterfall）
      await this._execute(this._runner)               // ← 执行插件的 apply/call
      this._error = undefined
    }
  } catch (reason) {
    this.ctx.logger.error(reason)
    this._error = reason
    this._runner.epoch = INACTIVE                   // 重载失败，标记为 INACTIVE
  }
  this._updateState(() => {
    if (this._runner.epoch === oldEpoch) {
      this.inertia = undefined                       // 重载成功，清除 inertia
    } else {
      this.inertia = this._unload()                   // epoch 已变，转为卸载
      return FiberState.UNLOADING
    }
  })
}
```

**难懂点**：
- **为什么 `await Promise.resolve()`**：确保后续代码在下一个微任务执行，给 disposer 队列留出执行空间
- **`_runner.epoch === oldEpoch` 检查**：重载是异步的，期间可能有新的 epoch 变更让本次重载失效；这个检查防止执行废弃的重载
- **`_resolveConfig` 支持 waterfall**：配置可以被监听器修改（插件间依赖的配置组合机制）
- **`this.inertia = undefined`**：重载完成后清空 inertia，允许后续 epoch 变更触发新的重载

## 链路二：工具调用的完整执行链路

### 调用栈回顾

```
execute() → schema 校验 → dispatchToolBody() → 瀑布流事件派发 → dispatchScheduledExecution() → startCall() → fillPool() → runGroup() → executeToolCalls() → step()
```

### 源码整合（按调用顺序）

#### 1. 工具入口与参数校验（`packages/core/tools/src/schema.ts:588`）

```ts
// 调用栈里的 execute() 实际调用了 schema 校验
// 源码位置：packages/core/tools/src/schema.ts
const validated = toolSchema.parse(arguments)      // ← 用 zod/schema 校验参数
state.bodyInvoked = true
const returned = await tool.execute(validated, exec)  // 校验通过后调用真正工具
```

**难懂点**：
- **为什么先校验**：模型传来的参数是 JSON，必须校验类型/形状，防止工具收到非法数据崩溃
- **`bodyInvoked` 标志**：标记「工具体已执行」，用于后续统计/计费/超时判断

#### 2. 工具分发入口（`packages/core/tools/src/index.ts:1549`）

```ts
private async dispatchToolBody(exec: ToolRunContext): Promise<ToolExecutionResult> {
  if (isAborted(signal)) {
    fused.dispose()
    return toolAbortedBeforeDispatchResult()
  }
  exec.signal = signal
  try {
    const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
    if (!tool) throw new ToolNotFoundError(exec.name)     // ← 找不到工具定义
    state.bodyInvoked = true
    const returned = await tool.execute(exec.arguments, exec)  // ← 真正执行工具
    const result = this.createSuccessResult(exec, tool, returned)
    return isAborted(signal) ? toolAbortedResult(result) : result
  } catch (error: unknown) {
    return toolErrorResult(error)
  } finally {
    fused.dispose()
    exec.signal = wrapperSignal
  }
}
```

**难懂点**：
- **`resolveExecution` 的作用**：根据 `exec.name`（工具名）+ `exec.agent`（调用者 agent）+ `exec.parent`（父 agent）解析出具体工具实例。**同一个工具名在不同 agent 下可能映射到不同实现**
- **`signal` 传递与恢复**：`exec.signal = signal` 把外部中止信号传给工具，`finally` 里恢复成 `wrapperSignal`，避免污染调用栈
- **`fused.dispose()`**：`fused` 是「熔断器」，超时/中止时会自动断开工具连接（如 HTTP 请求、子进程）

#### 3. 瀑布流事件派发（`packages/core/tools/src/index.ts:1573` + `vendor/cordis/src/events.ts:234-243`）

```ts
// packages/core/tools/src/index.ts:1573
const carrier = scopeTarget(this, exec.agent)
const result = await this.ctx.waterfall(
  carrier, 'tools/execute', mutableExec,
  () => this.dispatchToolBody(mutableExec),          // ← 瀑布流的目标函数
)

// vendor/cordis/src/events.ts:234-243
waterfall(...args: any[]) {
  const cbs = this.dispatch('waterfall', args)        // 收集所有 'waterfall' 监听器
  const inner = args.pop()                           // 弹出最终目标函数
  const next = () => {
    const cb = cbs.shift() ?? inner                   // 从监听器队列头部取一个，没有就执行最终目标
    return cb(...args)
  }
  args.push(next)
  return next()                                       // 开始链式执行
}
```

**难懂点**：
- **`waterfall` 是什么**：串行执行监听器，每个监听器可以修改传给下一个的数据。典型用途：工具策略（超时、权限、参数转换）按顺序修改 `exec`
- **`cbs.shift()` 链式执行**：从队列头部取监听器，执行后，递归调用 `next()`，直到队列空了，执行 `inner`（最终目标函数 `dispatchToolBody`）
- **与 `parallel` 的区别**：`parallel` 并发执行所有监听器（性能优先），`waterfall` 串行（可修改数据）

#### 4. 调度执行（`packages/core/tools/src/index.ts:1573-1599`）

```ts
private async dispatchScheduledExecution(exec: ToolRunContext): Promise<ScheduledToolDispatch> {
  try {
    const mutableExec = exec as MutableToolRunContext
    const carrier = scopeTarget(this, exec.agent)
    const result = await this.ctx.waterfall(
      carrier, 'tools/execute', mutableExec,
      () => this.dispatchToolBody(mutableExec),
    )
    const normalized = this.normalizeDispatchResult(exec, result)
    const deferredContexts = this.deferredContexts.get(exec)
    if (deferredContexts === undefined) throw new Error('tool registry scheduler invariant violated')
    const resultWithDeferredContexts: ToolExecutionResult = deferredContexts.length === 0
      ? normalized
      : this.markCanonical(exec, {
          ...normalized,
          additionalContexts: [
            ...deferredContexts,
            ...normalized.additionalContexts ?? [],
          ],
        })
    return {
      kind: 'post-result',
      result: this.callerCancelled(exec) && !resultWithDeferredContexts.isError
        ? this.cancellationResult(exec, resultWithDeferredContexts)
        : resultWithDeferredContexts,
    }
  } catch (error: unknown) {
    return { kind: 'final-result', result: toolErrorResult(error) }
  }
}
```

**难懂点**：
- **`deferredContexts` 是什么**：工具的「延迟上下文」——某些上下文（如流式响应的部分内容）只有在工具执行后才知道，在这里补全到结果里
- **`markCanonical`**：标记「规范化结果」，确保结果符合工具输出 schema（额外上下文被合并进来）
- **`kind: 'post-result'` vs `'final-result'`**：`post-result` 表示还需要 `postExecute`（后处理），`final-result` 表示已经是最终结果（失败时直接 final）

#### 5. 工具调用启动（`packages/core/agent-loop/src/tool-calls.ts:173-196`）

```ts
switch (prepared.kind) {
  case 'dispatch': {
    const promise = ctx.tools[TOOL_RUNTIME_SCHEDULER].dispatch(prepared.exec).then(
      (outcome) => {
        slots[index] = { exec: prepared.exec, result: outcome.result, needsPost: outcome.kind === 'post-result' }
        return index
      },
      (error: unknown) => {
        schedulerFailure ??= { error }
        return index
      },
    )
    inFlight.set(index, promise)                      // ← 记录正在执行的工具
    break
  }
  case 'post-result':
    slots[index] = { exec: prepared.exec, result: prepared.result, needsPost: true }
    break
  case 'final-result':
    slots[index] = { exec: prepared.exec, result: prepared.result, needsPost: false }
    break
}
```

**难懂点**：
- **`prepared.kind` 的三种状态**：`dispatch`（需要调度执行）、`post-result`（已经有结果，还需后处理）、`final-result`（最终结果，直接用）
- **`inFlight.set(index, promise)`**：记录「哪些工具正在执行」，用于 `fillPool()` 判断并发上限
- **`needsPost` 标志**：表示这个工具的结果还需要 `postExecute`（如流式输出的收尾）

#### 6. 工具池填充（`packages/core/agent-loop/src/tool-calls.ts:198-213`）

```ts
const fillPool = async (): Promise<void> => {
  while (!aborted && nextToStart < group.length && inFlight.size < maxParallelToolCalls) {
    const nextCall = group[nextToStart]!
    if (nextToStart > 0 && mode === 'parallel'
      && ctx.tools.executionMode(nextCall.exec).kind !== 'parallel') break
    await startCall(nextCall)                        // ← 启动一个工具调用
    nextToStart++
    await commitReady()                             // 提交已就绪的任务
    if (signal.aborted) aborted = true
  }
}

await fillPool()                                    // ← 填充工具池
await Promise.all(inFlight.values())                 // 等待所有工具完成
```

**难懂点**：
- **`maxParallelToolCalls` 并发上限**：同时最多执行 N 个工具，超过限制的等待
- **`mode === 'parallel'` 检查**：如果当前模式是 `parallel`，但某个工具的执行模式不是 `parallel`（如顺序依赖），暂停填充
- **`commitReady()`**：提交已就绪的任务（可能是 `post-result`/`final-result`），释放并发槽位

#### 7. 分组运行（`packages/core/agent-loop/src/tool-calls.ts:219`）

```ts
await fillPool()
await Promise.all(inFlight.values())
```

**难懂点**：
- **为什么要 `Promise.all(inFlight.values())`**：等待所有正在执行的工具完成（无论成功失败），确保下一轮模型请求能看到完整工具结果
- **与 `fillPool` 的配合**：`fillPool` 是「启动工具」，`Promise.all` 是「等待完成」，合起来就是「启动 → 等待 → 再启动下一批」的循环

#### 8. 落到 agent 的 `step()`（`packages/core/agent-loop/src/agent.ts:395`）

```ts
// tool-calls.ts:90
await executeToolCalls()

// agent.ts:395（简化版）
async step(): Promise<void> {
  const request = await this.llm.generate(this.current, signal)   // 请求模型
  const calls = parseToolCalls(request)                              // 解析工具调用
  const results = await this.executeToolCalls(calls)                // 执行工具
  this.current.appendHistory({ role: 'tool', results })             // 把结果写入历史
  return this.step()                                                 // 下一轮
}
```

**难懂点**：
- **`step()` 是「回合」**：一个 `step()` 包含「请求模型 → 解析工具调用 → 执行工具 → 收集结果 → 写入历史」一个完整闭环
- **递归调用 `this.step()`**：工具执行完后，继续下一轮模型请求，直到模型不需要更多工具调用
- **与工具池的关系**：`executeToolCalls()` 在一个 `step()` 内部，工具池是为了「同一回合的工具调用并发执行」

## 两链路的关键差异与联系

### 差异

| 维度 | 插件加载链路 | 工具执行链路 |
|---|---|---|
| **触发时机** | 插件注册/配置变更/依赖 fiber epoch 变化 | 模型发起工具调用 |
| **核心抽象** | Fiber（生命周期）+ Effect（注册-拆卸） | 瀑布流事件派发 + 工具池并发 |
| **异步特征** | 异步重载（`_reload` 是 Promise） | 异步执行（工具调用 + `postExecute`） |
| **传播模式** | Epoch 级联更新（依赖链） | 瀑布流串行（工具策略）+ 并发池（工具执行） |
| **失败处理** | 重载失败 → epoch 置 INACTIVE | 工具失败 → `isError` 结果，不中断其他工具 |

### 联系

1. **都用 `effect()` 注册生命周期**：
   - 插件加载：`ctx.plugin()` 用 `effect()` 注册 disposer
   - 工具执行：`startCall()` 里的 `fused.dispose()` 也依赖 effect 系统

2. **都用 `waterfall()` 修改数据**：
   - 插件加载：`_resolveConfig` 用 waterfall 让监听器修改配置
   - 工具执行：`dispatchScheduledExecution` 用 waterfall 让监听器修改 `exec`

3. **都用 `epoch`/`uid` 跟踪状态**：
   - 插件加载：epoch 是 fiber 的代际标记
   - 工具执行：`exec.id` 是工具调用的唯一标识
